# Genie Code instructions — Pipeline Optimization Factory

You optimize Databricks pipeline notebooks safely and provably. Follow this contract.

## 1. Scope & entry
- Work **one job at a time**. The user gives a `job_name`. Pull the job JSON (Jobs API) and
  auto-fill `opt_config` (see `config/example_job.yaml`). Process notebooks in **DAG order**.
- Never optimize more than one notebook at a time. Human approves before you implement (GATE 1)
  and before you promote (GATE 2).

## 2. Mandatory step order (per notebook)
1. `perf-profile` — diagnose the bottleneck (import the skill script; do not reimplement inline).
2. Detect `source_tables` (to pin) and `target_tables` (to clone); flag non-determinism.
   If the notebook is non-deterministic, STOP and report — do not auto-optimize.
3. Propose suggestions → **wait for human approval (GATE 1)**.
4. `optimize-notebook` — write v2 to `<ntb>_genie_opt_<timestamp>` in the dedicated folder.
5. `sandbox-setup` — shallow-clone targets into `sandbox_catalog` (WITH data for MERGE), pin
   inputs via time-travel, remap all writes to the sandbox. Never write to a production table.
6. Run v2 end-to-end against the sandbox.
7. `equivalence-check` — counts → column fingerprint → `EXCEPT ALL` both ways, step-by-step.
   The equivalence gate is HARD: if any step diverges beyond tolerance, mark `validate=failed`,
   write the insight, and DO NOT promote.
8. `perf-benchmark` — fair measurement (same compute, control cache, median of N). Promote only
   if equivalent AND faster/cheaper by `min_gain`.
9. **Wait for human approval (GATE 2)** before any promotion (PR/DAB).

## 3. Import, don't reimplement
Each SKILL.md tells you to import its `scripts/`. Import them — do NOT re-derive the equivalence
or sandbox logic inline. Determinism and safety depend on running the certified harness.

## 4. Audit contract (every step)
For every step call `audit_log()` with started → terminal (succeeded or failed+re-raise). Record:
job, notebook, step, status, change_type, equivalence result + method + rows compared,
perf_before/after (runtime, DBU, shuffle, spill), and a short NL **insight** (the *why* — why it
was slow, what you changed, why it is faster/equivalent). Write an insight on every equivalence
result and every failure.

## 5. Guardrails
- The baseline is the reference truth; you prove the candidate is equivalent **to it**.
- Never soften the equivalence tolerance to make a candidate pass. If a threshold is wrong, raise
  it in config with justification — do not move the check.
- Prefer neutral wording ("pipeline owner", "data engineer") in insights.
